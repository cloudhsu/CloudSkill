# CloudBox 7.6.18 Skill release evidence

## Scope

  `SKILL.md` Step 7 pointer.

## Owners and overlap

## RED evidence

Conversation-derived, 2026-08-15: splitting `developing-skills` into
`developing-skills` + `developing-eval` (v7.6.9-7.6.17) took 9 follow-up
patch releases to actually work end to end, because validator scripts had
hardcoded, transitive dependencies on the moved files that a direct grep for
the moved skill's own name never surfaced — a validator imported another
script, which imported another script, which hardcoded a path three hops
away. Passing the source repo's own check suite did not prove the split was
complete; only actually running the real downstream export pipeline did.
`safe-incremental-refactoring`'s existing "Shared-Consumer Before/After
State" section addresses multiple *known* consumers of a component; it does
not address a consumer reachable only by tracing an import/path chain
outward, or the distinction between in-repo test-suite evidence and
downstream-pipeline evidence.

## Minimal change

- New `references/evidence-checklist.md` section: "Transitive-Consumer
  Discovery Before a Split" — grep the moved item's name, then grep one hop
  further from anything that references it, repeat until a pass finds
  nothing new; distinguish "no result" from "not searched"; an in-repo test
  suite proves internal consistency, not that a downstream
  packaging/export/install step is complete. Counterexample retained for a
  moved item with no downstream step and no other script importing/hardcoding
  a path to it.
- `SKILL.md` Step 7: one-sentence pointer, matching the existing
  shared-consumer-table pointer's style.
- Iteration 2 revision (see below): added a further paragraph — the discovery
  methods above are a minimum, not a checklist that closes the question once
  satisfied; ask what's distinctive about the specific item being moved (a
  serializer whose output is later reconstructed by dotted path, an
  identifier persisted in a cache key, a schema version baked into stored
  data), since a consumer that reaches an item by what it *is* rather than by
  its name cannot be found by grepping harder.

## Distillation methodology (new for this repo)

Used Anthropic's `skill-creator` skill end-to-end instead of manual editing:
snapshot the pre-change skill as a baseline, draft the revision, write 4
realistic test prompts with objective assertions, spawn paired subagents
(revised skill vs. baseline) per prompt, grade against assertions, aggregate
into `benchmark.json`, and review qualitative outputs in a generated HTML
viewer — repeated for a second iteration after the first surfaced a real gap.

## Verification (iteration 1)

- 3 initial test prompts (transitive-split-audit, downstream-packaging-check,
  single-consumer-no-overreach — the last a deliberate counterexample/restraint
  check) plus 1 hardened adversarial variant (hardened-transitive-audit,
  designed to remove the earlier prompts' easy hooks: no packaging mention,
  claims identifier-level grep already done, non-security-flavored naming).
- Assertion pass rate: 12/12 (100%) in both configurations across all 4
  prompts — the drafted section did not change binary pass/fail outcomes,
  because the pre-existing skill (Shared-Consumer Before/After State +
  separate-refactor-from-behavior-change discipline) already generalized
  correctly on Claude Sonnet 5.
- Efficiency delta: with-skill responses were faster and used fewer tokens on
  average across all 4 prompts (largest gap: 57.8s/31.1k tokens vs.
  108.3s/35.1k tokens on the hardened case).
- QUALITATIVE FINDING (not captured by binary assertions): on the hardened
  case, the baseline independently surfaced a risk the drafted with-skill
  response never mentioned — a `__module__`/pickled-path identity change,
  reasoned from the moved function being named `serialize_snapshot`. The
  drafted response covered only the categories illustrated in its own text
  (import chains, re-exports, registries) — a real signal of anchoring on
  listed examples at the cost of open-ended, item-specific reasoning.
- Full `run_all_checks.py`: NOT RUN mid-iteration by design (skill-creator's
  loop tests behavior in isolated subagents, not the full repo pipeline);
  run once for real before this release (see below).

## Verification (iteration 2, after the anchoring fix)

- Same 4 prompts, re-run: revised skill vs. the iteration-1 draft (isolating
  the effect of the anchoring-fix paragraph specifically).
- Assertion pass rate: 12/12 (100%) again in both configurations.
- Anchoring gap: CLOSED WITH EVIDENCE. The revised with-skill response on the
  hardened case now contains a dedicated section ("Non-name-based
  consumers — this is the one I'd actually worry about here") independently
  reasoning from `serialize_snapshot`'s name to a pickling/persisted-path
  risk, with more concrete detail than the iteration-1 baseline that first
  surfaced it (names Celery/Redis/joblib-style pickling-under-the-hood cache
  layers, and a schema/module-identifier-string variant).
- Regression check: the counterexample case (single-consumer-no-overreach)
  stayed proportionate in content in both iterations — no over-triggering
  introduced.
- Efficiency: reversed from iteration 1 -- with-skill was slower on all 4
  prompts in iteration 2 (notably single-consumer-no-overreach: 77.1s vs.
  42.3s), a plausible cost of the added "ask what's distinctive" instruction
  causing more deliberation even on cases where nothing distinctive applies.
  N=1 per cell; not distinguished from run-to-run variance, disclosed as an
  open question rather than resolved.
- Full structural checks: `scripts/run_all_checks.py` PASS (run for real
  after the skill-creator loop, before release — see Release gate).
