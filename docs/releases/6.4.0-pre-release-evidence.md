# CloudBox 6.4.0 pre-release evidence

CloudBox 6.4.0 adds a deterministic lifecycle-template fast path without
creating another Plan Owner or weakening lifecycle, evidence, verification,
resume, reconciliation, or release gates.

## Delivered boundary

- `config/lifecycle-templates.json` is the sole template registry authority.
- Implemented templates are `lightweight-change`, `bounded-feature`, and
  `skill-evolution`; seven registered future IDs remain deferred and return
  `unsupported` without fallback.
- The selector/composer is pure. It has no task, model, persistence, network,
  Git, merge, tag, Release, or deployment authority.
- `development-process-tailoring` remains the sole lifecycle Plan Owner and the
  existing orchestration contract remains the durable state/reconciliation
  owner.
- Manual Eval ZIP exchange, privacy policy, unsupported and legacy retention,
  and explicit human review before formal Skill/Eval promotion remain intact.
- Bundle format and exporter version remain `2.0`; filename identity is
  unchanged. CloudBox product version remains provenance metadata rather than
  the compatibility discriminator. The 6.4 importer accepts a correctly named
  6.3-format-2.0 archive in an end-to-end fixture, and the current 6.4 exporter
  round trip remains covered.
- Export and Git Exchange derive contract metadata from candidate payloads and
  refuse mixed CloudBox/schema/runtime batches. Import validates supported
  bundle 2.0, exporter 2.0, candidate schema 1.0, exact manifest/payload
  CloudBox version and host/runtime agreement, filename identity, declared
  members, unique payload names, and hashes before publishing any candidate.
  Mismatch retains the whole archive as unsupported with no partial candidate
  output; Exchange push rejects duplicate payload names before remote access.
  This proves structural declaration consistency, not model reasoning quality.

## RED/GREEN evidence

The implementation plan preserved deterministic RED/GREEN for registry
authority, typed exclusions, direct selection, deferred refusal, owner/gate
conflict, stage partial-order composition, cycle detection, context-bound
selection, caller-resealed replay, selective invalidation, ordered lineage, and
fresh resolution after authority/source/risk changes.

The later exchange-contract increment also preserved focused RED/GREEN. A
manifest/payload CloudBox-version mismatch was accepted before correction, and
two pending files with the same archive member name were silently collapsed by
the Exchange hash map. The corrected validators reject CloudBox-version,
candidate-schema, and host/runtime disagreement before candidate publication;
they also reject duplicate archive member names before remote access. Focused
bundle, Exchange, interaction-import, and full deterministic checks pass.

The first exact-tip contract review then found that Exchange preflight checked
only metadata, malformed sanitization could escape as `TypeError`, and a later
publication failure could leave earlier archive outputs. Focused RED reproduced
all three. The correction now runs full structural and private-term validation
before remote access, rejects credential and local config-path metadata,
normalizes malformed sanitization as rejection evidence, and rolls back already
published outputs when an archive write fails. Provider/model execution remains
`NOT RUN`; this is deterministic contract evidence.

Final review found that ordinary Python equality aliased JSON `false` with
numeric `0` and `true` with numeric `1`. Exact admission and replan fixtures
failed before correction. The shared contract now uses canonical
type-preserving JSON identity; facts and risk mutations cover `false -> 0` and
`true -> 1`, while independent adversarial review also checked the reverse
directions.

The session initially promoted this implementation RED into three proposed
Skill behavior changes. Independent Skill review rejected that cross-layer
claim. Fresh pre-change blind cases showed the three existing owners already
produced the required behavior, so those edits were removed as
`NO_CHANGE_JUSTIFIED`. The observed governance failure became the separate
`DEVSK-BEH-017` RED; `developing-skills` now requires layer-typed RED/GREEN and
its post-change blind forward test passed. Exact prompts, outputs, worker IDs,
source revision, adjudication, and limitations are retained in
`docs/evolution/2026-08-12-typed-identity-skill-baseline-evidence.md`.

Provider-backed repository Runtime Eval was `NOT RUN`. Behavior-contract
validation and subagent forward tests are not represented as provider-family
diversity or whole-corpus Runtime Eval.

## Compatibility and rollback

Existing callers of the four-argument lifecycle `create_plan()` contract keep
their previous shape. Pre-correction template snapshot schema v1 is not admitted
as selected and must be regenerated; legacy plans without template resolution
remain supported. No data migration or automatic external adapter is added.
Rollback uses immutable `v6.3.0`.

## Exchange-format maturity signal

Treat exchange stability as a product-maturity indicator, not as proof from an
unchanged version label alone. Track bundle-schema stability across product
releases, backward importer window, end-to-end round-trip success, format-caused
manual-review and unsupported rates, migration frequency, filename/manifest/
hash identity stability, and deterministic recovery from duplicate, malformed,
collision, and interrupted input.

The 6.4 candidate supplies one positive increment: product version changes from
6.3 to 6.4 while bundle/exporter format remains 2.0, candidate schema remains
1.0, filename identity remains unchanged, current export/import passes, and a
correctly declared 6.3 archive is accepted by the 6.4 importer. Deliberate
CloudBox/schema/runtime mismatches fail before publication. This does not freeze
the format. Manual review,
unsupported retention, and legacy recovery remain until several releases and
real intake evidence show that format drift no longer drives manual handling.
