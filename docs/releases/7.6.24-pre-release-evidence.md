# CloudBox 7.6.24 pre-release evidence

Date: 2026-08-16 (Asia/Taipei)

## Scope

This is a follow-up optimization of the public Core `project-management-sync`
Skill using `skill-creator`. It does not add provider credentials, endpoints,
backlog records, task identifiers, or provider-backed mutations.

## Changes

- explicit `audit`, `dry-run`, `apply`, and `reconcile` execution modes;
- provider-adapter versus provider-neutral reconciliation responsibility split;
- per-field ownership and conflict policy for bidirectional synchronization;
- non-mutating capability discovery and fail-closed writes for unknown or
  unsupported versions;
- new `PMS-BEH-004` and `PMS-R04-unknown-version-read-only` coverage.

## Validation status

The `skill-creator` quick validator was invoked with both available Python
runtimes but could not start because the `yaml` module/PyYAML is unavailable.
JSON parsing, repository Skill lifecycle validation, plugin/packaging checks,
context-budget checks, portability checks, behavior-contract validation, and
the full native check suite are release gates and must pass on the final tip.

Final candidate results:

- Claude Code CLI 2.1.233, requested model alias `sonnet`; Qwen not used;
- routing forward-test: 4/4 expected primary selections, including the new
  unknown-version case;
- selected-skill behavior: 4/4 completed, deterministic rubric 100/100;
- privacy scan: PASS after allowing only reserved placeholders such as
  `actor@example.invalid`;
- context integrity: PASS, no truncation or overflow;
- `scripts/run_all_checks.py`: PASS — `All CloudSkill checks passed.`

The generic runtime summary also records that Claude did not return a canonical
provider model identity. That runner identity gate is reported separately and
does not change the observed `sonnet` CLI request, the 4/4 routing decisions,
or the behavior execution/rubric results above.

## Non-claims

This release does not claim that any real Vikunja, OpenProject, or Redmine
instance is compatible with an unknown version. It only strengthens the Skill
contract and synthetic evaluation coverage; real provider adapter contract
tests remain required before writes.

## Scope: `native-ios-game-rewrite` behavior-case expansion

The skill's only `application`-type behavior case (`NIGR-BEH-002`) previously
covered a single legacy-game shape (arcade/action scoring). That is the only
shape the 7.6.22 GREEN evidence (3/3 repeated runs, mean 97.1/100, recorded in
`docs/releases/7.6.22-pre-release-evidence.md`) actually exercised. This
change adds a second, structurally distinct `application` case
(`NIGR-BEH-004`, a multi-queue/multi-agent service-simulation shape) so the
skill's only application-level evidence stops resting on one gameplay domain,
and revises `NIGR-BEH-002`'s prompt to be explicit about a real, verifiable
constraint found in source (a bundled ad-mediation static library with no
arm64 slice) rather than a generic "old SDK" description.

### Changes

- `evals/behavior/cases/native-ios-game-rewrite.json`: `NIGR-BEH-002` revised,
  `NIGR-BEH-004` added (both `application` type); added top-level `"suite"`
  key so the case file is directly consumable by `run_runtime_evals.py
  --cases`.
- `evals/runtime/cases/game-distillation-behavior-rubrics.json`: new
  deterministic rubrics `NIGR-BEH-002` and `NIGR-BEH-004` (5 weighted
  criteria + 2 penalty patterns each), scoped narrowly enough that generic
  engineering advice does not pass by accident (e.g. requires an explicit
  architecture/arm64-slice check before treating a bundled static library as
  reusable, requires per-agent state modeling rather than a single aggregate
  counter for the service-simulation case).
- `.agents/skills/native-ios-game-rewrite/lifecycle.json`:
  `behavior_case_ids`/`behavior_case_types` refreshed via
  `scripts/manage_skill.py refresh --all`; notes updated to state plainly
  that the 7.6.22 97.1/100 figure does not cover the new or revised cases
  until they are separately evaluated (this document is that evaluation).

### GREEN results (skill loaded, `selected-skills` context mode)

Claude Code CLI, `claude-default` model alias, `num_ctx=12288`, 1 attempt per
case (single-repeat; not yet release-grade 3x-repeat evidence):

| Case | Score | Gate |
|---|---:|---|
| `NIGR-BEH-002` (arcade shape) | 90.0/100 | PASS |
| `NIGR-BEH-004` (service-simulation shape) | 85.0/100 | PASS |

### RED baseline attempt and an honest negative result

Following the 7.6.21/7.6.22 precedent ("remove the candidate Skill from
`SKILL_MANIFEST.json`, keep the same router/case/context"), both cases were
re-run with `native-ios-game-rewrite` temporarily removed from
`SKILL_MANIFEST.json` (backed up first, restored immediately after, verified
byte-identical via `diff` against the backup — `git diff` on the manifest
shows zero changes).

**Result: both cases scored identically to GREEN (90.0 and 85.0).** This is
not evidence the Skill has no effect — inspecting the routing decision shows
the router did not fall back to "no skill"; it composed three adjacent
Skills instead (`gameplay-core-modernization` as primary, with
`cross-platform-native-architecture` and `game-quality-and-release-gates` as
supporting) whose combined guidance happened to satisfy the same rubric
criteria. **This RED methodology does not establish a true zero-guidance
baseline for this Skill** — the router's own composability absorbed the
removal. A harder baseline (a general-purpose agent explicitly instructed not
to invoke any CloudBox Skill at all, run earlier in this session via a
separate `skill-creator` benchmark on the arcade-shaped case only) did show a
real, narrower gap on 4 assertion-style checks, but that is a different
harness and is not folded into this file's pass/fail gate.

### What this evidence does and does not support

- Supports: the Skill's guidance, when loaded, produces rubric-passing output
  on two structurally different legacy-game shapes, not just the one shape
  the original 7.6.22 evidence covered.
- Does not support: a claim that removing this Skill measurably degrades
  output quality — the manifest-removal RED methodology could not show that,
  for the structural reason above. Establishing that would require either a
  true no-CloudBox-Skill-at-all baseline harness (see the `skill-creator`
  comparison noted above) or a rubric criterion specific enough that the
  adjacent-Skill composition does not also satisfy it.
- Does not support: 3x-repeat release-grade variance evidence (this is a
  single attempt per case) or any claim about real Xcode build, device,
  signing, or store outcomes — the Skill's own forbidden-behavior checks
  explicitly forbid claiming those without execution evidence, and none was
  produced here.

Release judgment for this specific change: evidence supports keeping
`native-ios-game-rewrite` at `active` with broadened application coverage;
it does not by itself support any claim of measured improvement over its
prior state, and that limitation is recorded here rather than implied away.

## Scope: `indie-game-product-evolution` first RED/GREEN

New draft Skill (see `git log --grep indie-game-product-evolution`). This is
its first model evaluation since authoring; stage remains `draft` and this
evidence supports promotion review only, not automatic promotion.

### Setup

Claude Code CLI, `claude-default` model alias, 1 attempt per case (single-
repeat; not yet 3x-repeat release-grade). Routing: `router` context,
`num_ctx=8192`, cases in `evals/runtime/cases/igpe-routing.json` (mirrors
`evals/skill-routing-cases.csv` IGPE-01/IGPE-NEG-01/IGPE-NEG-02). Behavior:
`selected-skills` context, `num_ctx=12288`, case `IGPE-BEH-002` (application),
graded against the new `IGPE-BEH-002` rubric in
`game-distillation-behavior-rubrics.json`.

### GREEN (Skill loaded)

| Eval | Result |
|---|---|
| Routing (3 cases) | 3/3 primary-skill accuracy, contract valid, execution order correct, zero forbidden-skill violations |
| Behavior `IGPE-BEH-002` | 100.0/100 — all 5 rubric criteria (archetype-fit, successor-decision, monetization-redesign, save-continuity, capability-stop) passed in full |

### RED (Skill removed from `SKILL_MANIFEST.json`, restored + diff-verified after)

| Eval | Result |
|---|---|
| Routing (3 cases) | 2/3 primary-skill accuracy (gate FAIL). `IGPE-01` (the case that needs this Skill) routed to `primary_skill: null` — the router correctly declined to force-fit an adjacent Skill rather than mis-routing, but that is still a real, measured accuracy loss against the expected contract. `IGPE-NEG-01`/`IGPE-NEG-02` were unaffected (they don't need this Skill). |
| Behavior `IGPE-BEH-002` | 60.0/100 (gate FAIL). Criterion breakdown: `archetype-fit` 20/20 pass, `monetization-redesign` 20/20 pass, `successor-decision` 5/20 partial, `save-continuity` 5/20 partial, `capability-stop` 10/20 partial. |

**This is a genuine, measured gap** — unlike `native-ios-game-rewrite`'s
same-day RED attempt (see above), no adjacent Skill absorbed the removal;
the router left `IGPE-01` unrouted rather than mis-assigning it. The gap is
concentrated exactly where a decision-shape Skill should add value: a
general-purpose baseline still named the archetype and redesigned
monetization competently on its own (those criteria stayed full-score even
without the Skill), but did not reliably produce the Skill's specific,
non-obvious defaults — stating the new design's acceptance bar explicitly,
defaulting to no save migration with an explicit stated decision (rather
than silence), and hitting the capability-tier-plus-stop-condition output
shape. That is the actual, specific value this Skill is adding, not a
diffuse "the model is smarter with the Skill" claim.

### What this evidence does and does not support

- Supports: `indie-game-product-evolution` produces a measurable behavior
  and routing improvement over no-Skill baseline, concentrated in specific,
  named decision-shape criteria, not general engineering competence.
- Does not support: promotion to `stable` or public Core — this is one
  attempt per case, not 3x-repeat release-grade evidence, and no adjacent-
  Skill regression sweep (comparable to `game-asset-resolution-audit`'s
  `GARA-R02-greenfield-art-control` pattern) has been run to confirm this
  Skill does not over-trigger on adjacent product-decision-shaped requests.
- Does not support: any claim about real-world product outcomes — the
  rubric measures deterministic evidence-coverage in the written answer,
  not whether the resulting product decision was actually correct for any
  real game.

Release judgment for this specific change: evidence supports keeping
`indie-game-product-evolution` at `draft` with real RED/GREEN evidence now
attached (previously none existed); promotion to `experimental` or `active`
would need the repeat-count and adjacent-regression evidence named above,
which this pass deliberately did not attempt.

## Scope: `legacy-game-product-archaeology` second application case + RED/GREEN

Follow-up to the `native-ios-game-rewrite` and `indie-game-product-evolution`
evidence above, closing a gap flagged during that work: this Skill's only
`application` case (`LGPA-BEH-002`) covered one archetype shape (mixed
evidence with a requirements document and dated backups). Added
`LGPA-BEH-004`, a structurally different archetype (a staged platformer's
economy: currency-gated unlocks, a non-functional placeholder stage, two
control-scheme-keyed per-stage record fields, a client-side-only IAP grant),
with no design document at all — a source-only reconstruction rather than a
mixed-evidence one.

### Setup

Claude Code CLI, `claude-default` model alias, 1 attempt per case (single-
repeat). `selected-skills` context, `num_ctx=12288`. New rubrics `LGPA-BEH-002`
and `LGPA-BEH-004` added to `game-distillation-behavior-rubrics.json`.

### Results

| Case | GREEN (skill loaded) | RED (skill removed from manifest, restored + diff-verified after) |
|---|---:|---:|
| `LGPA-BEH-002` (mixed evidence, requirements doc) | 90.0/100 | 75.0/100 (passes gate at exactly the threshold) |
| `LGPA-BEH-004` (source-only, economy archetype) | 100.0/100 | 100.0/100 (identical) |

### What actually happened, and why this is a distinct pattern from both prior results

Both RED runs routed to `gameplay-core-modernization` as a substitute (for
`LGPA-BEH-002`, with `game-asset-resolution-audit` also selected as
supporting) — the same graceful-degradation pattern observed in
`native-ios-game-rewrite`'s RED attempt, not a true no-guidance baseline.

- `LGPA-BEH-004`: the substitute fully satisfied every rubric criterion.
  `gameplay-core-modernization`'s own extraction discipline (state ownership,
  evidence citation) apparently covers this archetype's archaeology needs
  just as completely as the dedicated Skill does. Zero measured gap.
- `LGPA-BEH-002`: GREEN itself was not a clean 100 (its own `next`
  criterion — smallest safe next slice with explicit unknowns — scored
  partial, 10/20, the same as RED; this looks like a rubric-strictness
  property of that one criterion, not a Skill regression, since it did not
  move between conditions). The one criterion that did move is `map`
  (responsibility and state-owner map): full pass under GREEN, partial
  under RED. That is the entire 15-point gap — a real, narrow,
  single-criterion difference, not a broad quality drop.

### What this evidence does and does not support

- Supports: `legacy-game-product-archaeology` and `gameplay-core-modernization`
  produce near-identical output quality on these two archetypes when either
  one is asked to do archaeology-shaped work, with the sole measured
  exception being explicit responsibility/state-owner mapping on the
  mixed-evidence archetype.
- Raises, rather than resolves, a real question worth a deliberate decision
  rather than silent acceptance: is this close an acceptable degree of
  scope overlap between two `active` Skills (per this Skill's own
  `next_review_triggers`, "a new adjacent skill creates scope overlap" is
  an explicit review trigger — this evidence is exactly that trigger firing,
  even though `gameplay-core-modernization` is not new), or should
  `legacy-game-product-archaeology`'s SKILL.md sharpen what specifically it
  requires (e.g. the responsibility/state-owner map as a named required
  artifact) that a general extraction-focused Skill does not reliably
  produce on its own? Not resolved here — flagged for the next review.
- Does not support: any change to either Skill's `active` stage from this
  evidence alone; single-attempt, no repeat, no formal side-by-side
  comparison of the two Skills' SKILL.md scope boundaries.

### Decision (2026-08-17)

Accept the overlap as acceptable redundancy; no SKILL.md change to either
`legacy-game-product-archaeology` or `gameplay-core-modernization`. The two
Skills are sequential collaborators by design (archaeology output feeds
extraction input), so sharing instructional ground on state ownership and
characterization-before-change is expected rather than a defect. The
measured gap is narrow -- one rubric criterion (`map`), one archetype
(mixed-evidence) -- and `gameplay-core-modernization` already absorbing most
archaeology-shaped work when `legacy-game-product-archaeology` is
unavailable is graceful degradation, not a routing failure. Revisit only if
a future case widens the gap beyond the single `map` criterion, or a real
misroute (not RED-substitution) is observed. Decided by the user; recorded
in `.agents/skills/legacy-game-product-archaeology/lifecycle.json`.

## Scope: `indie-game-product-evolution` release-grade evidence and promotion to `active`

Follow-up to the first-pass RED/GREEN above. Adds repeat-count evidence and
an adjacent-regression sweep, then promotes the Skill from `draft` to
`active` on the strength of that evidence, per
`developing-skills/references/skill-lifecycle-standard.md`'s stage table
("active: repeatable GREEN evidence and adjacent regressions").

### Adjacent-regression controls added

Two new negative routing cases in `evals/runtime/cases/igpe-routing.json`
(and mirrored in `evals/skill-routing-cases.csv`), testing that this Skill
does not over-trigger on requests that belong to specific neighboring
Skills once the product decision is already settled or was never in
question:

- `IGPE-NEG-03-native-rewrite-control`: scope/monetization/save decisions
  already made, request is now purely the native iOS implementation ->
  expected primary `native-ios-game-rewrite`.
- `IGPE-NEG-04-greenfield-control`: a fully-specified greenfield brief with
  no legacy anchor and no scope/monetization/save ambiguity, request is
  purely engine architecture -> expected primary
  `cross-platform-engine-architecture`.

### Results (Claude Code CLI, `claude-default`, `repeat=3`)

| Eval | Result |
|---|---|
| Routing, 5 cases x 3 attempts = 15 records | 15/15 (100%) on every metric: primary-skill accuracy, contract valid, execution order, zero forbidden-skill violations, zero router self-inclusion. Both new adjacent-regression controls passed on all 3 attempts each. |
| Behavior `IGPE-BEH-002`, 3 attempts | Scores 100.0 / 90.0 / 100.0 -- mean 96.7, population stdev 4.7. All 3 pass the 75-point gate. Attempt 2's only partial criterion was `capability-stop` (10/20); everything else full score on all 3 attempts. |

This mean/stdev is directly comparable to the 7.6.22 four-skill benchmark's
"mean 97.1/100" figure recorded in `docs/releases/7.6.22-pre-release-evidence.md`.

### Promotion decision

`indie-game-product-evolution` is promoted `draft` -> `active` in
`.agents/skills/indie-game-product-evolution/lifecycle.json` and
`config/skill-domain-catalog.json`. This is the first `active` Skill in the
`product-dev` domain.

**Disclosed release limitations** (per the lifecycle standard's "Release
truth" section -- reported rather than smoothed over):

- Application-level behavior evidence still covers one archetype
  (`IGPE-BEH-002`, the staged-platformer-with-economy shape). Both
  `native-ios-game-rewrite` and `legacy-game-product-archaeology` were
  broadened to two structurally distinct archetypes earlier this same day;
  `indie-game-product-evolution` was not, since its RED result already
  showed a clear, real gap on the existing single case and broadening was
  judged lower priority than closing out release-grade evidence on what
  already existed. A second archetype is a reasonable next-review item.
- No CI validation and no install smoke test were performed -- this is
  local Claude Code CLI execution evidence only.
- The deterministic rubric measures evidence-coverage keyword patterns in
  the written answer, not full semantic correctness or any real-world
  product outcome -- unchanged limitation from the first-pass evidence
  above.

### Packaging gap found and fixed during promotion

While promoting, `config/skill-distribution.json` (the sole distribution
authority per `docs/SKILL_TAXONOMY.md`) was found to have no entry at all for
`indie-game-product-evolution` -- the earlier draft-authoring pass had
updated `config/skill-domain-catalog.json`'s secondary `distribution` field
but not the authoritative one, so the Skill was silently absent from both
the private Codex plugin projection and the private Claude plugin's
`skills` array/symlink (`private-plugin/skills/indie-game-product-evolution`
did not exist). Added the `evolution-pack` entry, the symlink, and both
`private-plugin/.claude-plugin/plugin.json` /
`private-plugin/.codex-plugin/plugin.json` array entries.
`scripts/validate_plugins.py` now passes; it would have caught this on the
next CI run regardless, but promotion is the point this got checked.
