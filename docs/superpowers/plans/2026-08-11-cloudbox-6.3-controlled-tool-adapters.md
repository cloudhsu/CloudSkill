# CloudBox 6.3 Controlled Tool Adapters Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a controlled local CLI execution broker with a versioned adapter contract, durable recovery semantics, and a Git vertical slice governed by CloudBox's adaptive lifecycle owner.

**Architecture:** `development-process-tailoring` owns a durable versioned plan; a broker validates registered capability invocations and authority before launching a narrow adapter; the adapter returns bounded structured evidence; the external system remains authoritative and ambiguous completion enters reconciliation before retry. The initial transport is local CLI, with contracts kept transport-neutral for later MCP support.

**Tech Stack:** Python 3.9-compatible standard library, JSON Schema contracts, Git CLI, repository-native validators and Behavior Evals.

## Global Constraints

- Do not expose arbitrary shell command execution or model-selected executables.
- Do not write private URLs, credentials, secret values, personal data, or sensitive payloads to repository files, Evals, logs, or model-visible results.
- Resolve paths before execution and restrict them to declared roots.
- Treat external state as authoritative; timeout or transport loss produces `UNCERTAIN`, never an automatic retry.
- Every mutation requires an authority grant, stable `action_id`, idempotency semantics, bounded attempts, and reconciliation support.
- Preserve the existing manual Eval bundle import command and behavior.
- Integration tests operate only on temporary Git repositories and fixture bundles.
- MCP, live GitHub mutation, NAS polling, arbitrary shell, and public/private package splitting are out of scope.
- Material Skill behavior changes require repeatable RED evidence before instruction edits and the same case GREEN afterward.
- Keep Python syntax compatible with the repository's supported installation and validation environments.
- Update `CLOUDSKILL_AGENT_HANDOFF.md` and `docs/CLOUDSKILL_CHANGE_HISTORY.md` whenever continuation state, open failure layer, or release decision changes.

## Plan-owner Re-planning Rules

The implementation may continue autonomously while failures stay within the approved design and are reversible. The plan owner must stop and request direction when any of these occurs:

- the solution requires arbitrary shell, a live remote mutation not listed in scope, or broader authority;
- a private endpoint, credential, sensitive payload, or personal data may have entered a tracked or model-visible artifact;
- action reconciliation cannot distinguish completed from incomplete external state;
- a required migration or rollback path is undefined;
- the authoritative registry would need more than one writer or competing policy owner;
- the release gate remains blocked after bounded, evidenced correction attempts;
- the public/private split would need to begin before the user resumes that deferred decision.

For ordinary test failures, contract mistakes, review findings, or CI defects, preserve the failing evidence, re-enter the stage identified by `classify_failure`/`classify_tool_event`, update the durable handoff, and continue from the first unproven step.
