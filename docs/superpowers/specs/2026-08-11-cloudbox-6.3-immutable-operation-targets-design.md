# CloudBox 6.3 Immutable Operation Targets Design

## Decision

CloudBox controlled mutating actions bind an immutable, content-addressed
`operation_targets` object before authorization or execution. Execution, retry,
and reconciliation use exactly that object. A changed Git remote, later commit,
or newly arrived bundle requires a new action identity.

This revision replaces the incomplete 6.3 v1 candidate contract. It does not
change the existing manual Eval bundle import command, add GitHub mutation,
introduce polling, or broaden the adapter into arbitrary shell execution.

## Pressure and authority

The authoritative question is whether the side effect declared by the original
action completed. Current external state alone cannot answer that question when
the remote or inbox may change after execution. Therefore:

- the host authorizes roots, endpoint references, action identity, and the
  prepare operation;
- a read-only prepare phase resolves mutable external state into immutable
  targets;
- the lifecycle owner authorizes that exact target digest;
- the adapter executes and reconciles only those targets;
- the durable action owns target identity and per-target evidence;
- Git and the Eval Inbox remain authoritative for observed external state.

No model selects paths, URLs, executable arguments, ref names, archive names,
or hashes after the target set is prepared.

## Contract v2

The invocation contract becomes `2.0` and requires:

```json
{
  "operation_targets": {
    "kind": "git-fetch-refs",
    "digest": "<canonical-sha256>",
    "items": []
  }
}
```

`digest` is SHA-256 over canonical JSON containing `kind` and `items`, excluding
the digest field itself. Items have closed schemas, stable ordering, bounded
counts, and no secret endpoint values. The broker recomputes the digest and
includes it in `input_hash`, the idempotency reservation, and durable state.

The durable action schema becomes version 2 and stores the complete bounded
`operation_targets` plus `target_evidence`. Evidence entries identify the target
digest and individual target key; they cannot be attached to another action or
target revision.

## Prepare boundary

The CLI adds `tool prepare`. Prepare is read-only and does not create an
authorized or executable action. It validates the registry, roots, endpoint
reference, adapter provenance, and capability arguments, then emits a bounded v2
invocation containing immutable targets. Operators may inspect and authorize
that artifact before calling `tool invoke`.

`tool invoke` and `tool reconcile` reject missing targets, target digest drift,
v1 invocations, and v1 durable checkpoints. They never silently prepare targets
because doing so after authorization would change the approved operation.

## Git fetch targets

Prepare validates that the named remote exists and its resolved URL exactly
matches the host-provided `SOURCE_REMOTE_URL`. It obtains the advertised heads
without mutation and produces sorted items:

```json
{
  "ref": "refs/heads/main",
  "object_id": "<40-or-64-hex Git object id>"
}
```

Execution fetches the explicit ref/object targets without tags and verifies each
resulting `refs/remotes/<remote>/<branch>` equals the prepared object ID. It does
not treat newly advertised remote heads as part of the action. A target that is
no longer fetchable is a confirmed failure only when Git provides definitive
evidence; transport and observation failures remain `UNCERTAIN`.

Reconciliation checks local remote-tracking refs only against the prepared
items. A remote advancing after the original action cannot invalidate successful
completion. An empty prepared item set succeeds when the corresponding local
remote-tracking set is empty. Extra local refs are not removed or attributed to
this action unless their deletion was represented by an explicit prepared
target in a later contract revision; prune semantics are excluded from this
slice.

## Eval bundle targets

Prepare scans only direct `imports/*.zip` files under the validated Eval Inbox
and produces sorted items:

```json
{
  "relative_path": "imports/example.zip",
  "sha256": "<archive-sha256>",
  "size_bytes": 1234
}
```

Execution opens only the listed files, rejects path escape, missing files,
symlinks, size drift, or hash drift, and calls the existing importer for exactly
those archives. Archives arriving after prepare are untouched and require a new
action. Per-archive evidence records the immutable hash and final queue outcome
or processed/unsupported destination.

Reconciliation classifies each prepared archive independently:

- matching archive still in `imports/`: `OBSERVED_PENDING`;
- matching archive and evidence-backed destination/sidecar: completed;
- missing archive without matching completion evidence: `UNCERTAIN`;
- content at the same relative path with a different hash: identity conflict and
  `BLOCKED`;
- any pending or uncertain item keeps the whole action non-terminal.

The existing manual command continues to scan the inbox dynamically. It is an
operator workflow, not a durable controlled action, and remains compatible with
current supported bundle versions.

## Compatibility and migration

The candidate has not been released, so registry, invocation, action, and
adapter protocol versions move together to v2 without a production data
migration. Nevertheless, local v1 checkpoints may exist from development:

- v1 terminal records remain readable for diagnostics but cannot be reopened;
- v1 non-terminal records return `BLOCKED` with a command-level explanation to
  inspect external state manually and create a new v2 action;
- the broker never deletes or rewrites v1 evidence;
- legacy bundle formats continue through the existing unsupported/manual queues.

## Failure and lifecycle routing

- Target preparation failure: `BLOCKED`; no action or mutation exists.
- Authorization or target digest mismatch: `BLOCKED` and re-plan.
- Definite execution rejection before side effect: `FAILED`, retryable only
  within policy.
- Timeout, process loss, missing completion evidence, or observation failure:
  `UNCERTAIN`, then reconcile the immutable targets.
- Contract, state-authority, or recovery-model mismatch: return to architecture.

Retries retain the same target digest, action ID, idempotency reservation,
adapter version, provenance, authority grant, and attempt budget.

## Security and privacy

Remote URLs and configuration paths remain host-resolved secret values and are
represented only by fingerprints in action identity. Bundle paths are relative
to the approved Inbox root. Target lists are bounded by registry policy before
serialization. Adapter output remains size-bounded and secret-redacted.

## RED/GREEN evidence

RED must reproduce:

1. a remote advancing after a successful-but-uncertain fetch is falsely marked
   incomplete by the v1 live-head comparison;
2. an archive arriving after action creation is consumed by the v1 inbox-wide
   import;
3. a same-name archive replacement is not distinguished from the original;
4. invoke without an authorized target digest can mutate state;
5. a v1 non-terminal checkpoint can enter a v2 execution/reconciliation path.

GREEN must prove:

- canonical target digest validation and negative drift mutation;
- prepare is read-only and bounded;
- execute and reconcile use only prepared fetch refs/archive hashes;
- late remote changes and late bundle arrivals do not change original outcome;
- missing, replaced, partial, duplicate, timeout, and restart cases preserve
  correct durable state and attempt counts;
- manual import compatibility remains unchanged;
- the complete deterministic suite passes twice before fresh L1 review.

## Release gate

Version synchronization to 6.3.0 remains prohibited until contract v2 passes
focused and complete deterministic checks and a fresh exact-tip
`L1_CROSS_FAMILY_2X2` review. Failed earlier review cells are diagnostic evidence
and do not count toward achieved assurance.
