# CloudBox 6.0 Evidence-Gated Evolution Design

Date: 2026-08-09
Status: Approved for specification; implementation remains evidence-gated
Branch: `feat/cloudbox-6.0-evidence-gated-evolution-20260809`

## Objective

Evolve CloudBox from 5.8.0 toward a defensible 6.0.0 release by improving task
continuity, Skill-development evidence, hosted multi-model evaluation, lifecycle
truth, and release lineage. The version is earned by a coherent public contract
boundary and verified behavior; changing version metadata alone is not success.

The user authorizes push, PR creation, merge, tag, and GitHub Release only after
all defined gates pass. Any unresolved authority/safety veto, invalid case,
provider degradation, CI failure, lineage conflict, or missing major-version
justification stops delivery at a reviewable release candidate.

## Evidence Baseline

Repository-verified state at design time:

- `HEAD`, local `main`, and `origin/main` are at `6356a00`.
- The working tree contained preserved, uncommitted task-continuity handoff and
  change-history updates; they moved with this single-purpose branch.
- Repository version surfaces report 5.8.0.
- The official 5.8.0 release is recorded in repository documents, but the local
  tag set does not currently contain `v5.8.0`; remote tag/release lineage must be
  verified before 6.0 release work relies on it.
- Existing live Runtime Behavior scoring is R07-focused. It does not establish
  behavioral coverage for all 19 Skills.
- GPT-5.6 Luna, Terra, and Sol supported the two-layer task-continuity direction.
- Claude Sonnet 5 and Opus 5 returned `MANUAL_REQUIRED`: the direction is sound,
  but reproducible baseline RED cases must precede any instruction change.
- Claude bounded plain-output calls work. Long-prompt and `--json-schema` paths
  have produced zero-token, misleading `Not logged in` failures despite valid
  authentication; this is a transport/output-contract defect, not a semantic
  verdict.

Unavailable evidence:

- The byte-identical packet used by the earlier GPT judges was not persisted.
- A full Behavior execution baseline for every Skill does not exist.
- Host/plugin reload evidence for a 6.0 candidate does not exist.

## Chosen Evolution Strategy

Use targeted RED/GREEN evaluation during development, then bounded full scoring
at the release-candidate boundary.

Rejected alternatives:

1. **Full 19-Skill 2x2 scoring first.** Rejected because most Skills lack the
   mature executable Runtime rubric needed to interpret a score, and the cost
   would be paid before a change surface exists.
2. **Edit Skills first and score once at the end.** Rejected because it cannot
   establish causal behavior improvement and violates RED-before-edit policy.

## Architectural Boundaries

### Global task-continuity invariant

The host-level invariant applies even when no CloudBox Skill is routed. It owns
only these decisions:

- retain, replace, or explicitly close the unfinished parent objective;
- preserve the existing authority envelope across `continue`, handoff, restart,
  and side questions;
- avoid treating continuation as authority to publish, deploy, delete, or send;
- after a side answer, resume the parent or truthfully state why it is paused;
- consult an identified durable source of truth before relying on chat memory.

It must not implement domain-specific reconciliation, repository release flow,
or Runtime Eval continuation.

### Specialist method ownership

`agent-development-process` owns the detailed method for task-state classes,
authority, durable/observable state reconciliation, dependencies, safe resumption,
completion criteria, evaluation, and operation.

Supporting owners remain narrow:

- `coding-agent-project-governance`: repository handoff, branches/worktrees,
  evidence truth, and release control.
- `local-runtime-eval-debugging`: Runtime Eval process and artifact continuation.
- `developing-skills`: RED/GREEN evidence and Skill lifecycle changes.
- `runtime-evaluation-engineering`: executable case validity, graders, panel
  protocol, and release interpretation.

No standalone task-continuity Skill will be created unless repeatable evidence
shows an independently routable family and expanding the existing owner would
reduce cohesion.

### Host-level evaluation contract

The existing Skill-scoped Behavior schema cannot truthfully model an ordinary
no-Skill, multi-turn workflow or a consequential tool attempt. Add a separate,
small host-level task-continuity contract with:

- ordered transcript turns;
- durable-state fixture and freshness metadata;
- initial parent-task state;
- authority/allowed-action envelope;
- prohibited actions;
- observable fake-tool attempts;
- expected parent status and final response behavior;
- required and forbidden outcomes;
- runtime/model/context/prompt hashes and raw trace/result.

The fake publish tool must be non-mutating. An unauthorized attempt is recorded
as RED evidence without changing an external repository or release.

Do not add ordinary continuation to the routing CSV. Requiring
`agent-development-process` to route would conceal the host-level coverage gap.

## Evolution Increments

### Increment A — Baseline case contract

Create the host-level contract, validator, result template, fake consequential
tool recorder, and specialist-method Behavior cases. Establish baseline against
unmodified behavior before changing instructions.

Primary cases:

- `continue` without publish authority;
- available durable handoff ignored;
- side question incorrectly treated as parent completion.

Controls:

- explicit cancellation;
- explicit pivot to a new task;
- explicit publish/ship authority;
- side question explicitly promoted to the new parent;
- already-completed parent;
- no identifiable parent or source of truth;
- harmless prose continuation without consequential action.

`continue -> publish authority` is the first safety baseline. Existing approval
guidance may already pass it; a passing baseline narrows the proposed change
rather than being relabeled as RED.

### Increment B — Minimum global invariant

Only after a host-level RED is reproduced, modify the authoritative global
instruction location with the smallest wording that closes that failure. Run the
same RED cases and all controls. Do not duplicate specialist reconciliation
logic globally.

### Increment C — Specialist continuity method

Run the specialist cases against the current `agent-development-process` Skill.
Only demonstrated failures may justify adding task classification, durable versus
observable reconciliation, dependency-ready resumption, completion truth, and
authority preservation. Run recognition, application, counterexample, and
repository-governance adjacency cases.

### Increment D — Executable 2x2 and cost ledger

Add a provider-neutral panel record and one coordinator-owned combined report.
Workers use immutable packets, blinded labels, unique outputs, least capability,
and no shared stable writer.

Required ledger fields include:

- experiment/stage/case/role IDs;
- packet, prompt, rubric, candidate, and raw-output hashes;
- provider/family, requested alias, and canonical returned model;
- adapter/CLI version and transport mode;
- input/cache/output/reasoning tokens when exposed;
- provider-reported or dated estimated cost and currency;
- latency, attempts, retries, fallback, and failure layer;
- verdict, unique/blocking findings, and adjudication link.

Provider scores remain separate and are never averaged into one quality score.

For Claude, preflight authentication separately. Permit at most one idempotent
retry after a valid preflight. The supported fallback is a separately hashed,
bounded plain-output prompt followed by local schema validation. If shortening
changes evidence content, it is a new experiment rather than the same packet.

### Increment E — Lifecycle and release truth

Audit lifecycle metadata semantically. Do not mass-refresh `introduced_version`,
`last_reviewed_version`, stage, or evidence merely to make validation green.

Define the 6.0 compatibility boundary, migration/rollback, supported install
surfaces, exclusions, and public contract changes. Candidate major boundaries
include the new host-level evaluation contract, continuity authority contract,
panel evidence/ledger contract, and corrected lifecycle/release evidence model.
If these do not constitute a coherent public contract change, stop and propose a
compatible 5.9.0 release instead of mislabeling it 6.0.0.

Separate:

- pre-release evidence, which can describe only facts true before tagging; and
- post-release operational record, which verifies merge, tag, release artifact,
  hashes, and published state after they occur.

An unpublished internal 5.9.0 version is forbidden. Development remains
unreleased until a real version decision.

### Increment RC — Bounded full verification and release

Run all deterministic/static/routing checks. Run hosted full routing on the
affected provider families and Behavior execution for materially changed owners
plus adjacent controls. Run whole-corpus Behavior only if a shared Router,
Behavior contract, context assembly, grader, or orchestration change creates a
credible cross-owner blast radius.

Use the complete 2x2 panel for authority, safety, routing-owner, or release
decisions. Release only from the exact reviewed/CI-green commit.

## Hosted Evaluation Ladder

1. Offline case/schema/contract validation and deterministic regrade: USD 0.
2. Targeted RED with one efficient hosted model, one call.
3. Cross-family efficient confirmation when a material RED is valid.
4. Minimal patch by one writer.
5. Targeted blinded GREEN with efficient judges from both families.
6. Escalate to GPT frontier and Claude Opus only for authority, safety,
   routing-owner, disputed expected-answer, material release impact, or
   cross-family disagreement.
7. Repeat only a disputed cell when stochastic instability can change the
   decision; use three total attempts for that cell.
8. At RC, execute provider-specific bounded full scoring for the impacted
   surface and a release-significant 2x2 packet.

The intended 2x2 is one efficient and one frontier judge from each of GPT and
Claude. The candidate producer and patch author are not judges. Judges cannot see
each other's verdicts before outputs are frozen. Safety, authority, privacy,
unsupported-claim, and evidence-lineage findings are vetoes requiring explicit
adjudication, not votes.

## Cost Controls and Reporting

Before every paid stage, declare:

- planned provider/model/call count;
- maximum repetitions;
- stage purpose and stop condition;
- remaining budget when a user budget exists.

After every stage, report:

- successful, zero-token failed, and retried calls separately;
- canonical model identities;
- provider-reported cost per call and stage total;
- token/cache usage and latency where exposed;
- result state and whether another call could change the decision.

No local/Ollama runs are planned. Budget exhaustion or provider degradation
produces an incomplete panel and cannot be converted to PASS.

## Failure Handling and Stop Conditions

Diagnose the earliest layer first:

1. infrastructure/authentication/provider availability;
2. context assembly/transport;
3. output contract;
4. case validity;
5. model discrimination;
6. Skill/global instruction;
7. deterministic grader;
8. semantic judge;
9. release interpretation.

Stop model calls when an offline defect is found. Stop adding judges when the
latest cross-family pair adds no decision-relevant finding, or when another run
cannot change release state.

Release states are `PASS`, `FAIL`, `BLOCKED`, `AMBIGUOUS`, and
`MANUAL_REQUIRED`. A planned 2x2 with a blocked worker is reported as degraded,
not complete.

## Version and Delivery Flow

1. Preserve this design and prior handoff changes on the single-purpose branch.
2. Verify remote 5.8.0 tag/release lineage before setting a 6.0 base.
3. Execute each increment as a reversible RED/GREEN commit series.
4. Keep the stable Runtime ZIP and combined panel report single-writer.
5. Refresh lifecycle/manifest output only after evidence is truthful.
6. Run repository checks twice when generated-file stability is relevant.
7. Smoke-install Codex and Claude plugin packages from the exact candidate.
8. Produce pre-release evidence with hashes and explicit NOT RUN items.
9. Obtain independent diff review and user-visible release summary.
10. Push branch and create PR; require CI on the exact tip.
11. Merge only with no open veto or failing gate.
12. Create and verify annotated `v6.0.0` tag and official GitHub Release.
13. Add a separate post-release operational record and verify remote state.

Rollback uses the verified prior 5.8.0 release artifact/tag and documented
installation recovery. Host/plugin reload remains `NOT RUN` unless actually
performed.

## Acceptance Gates

The 6.0 release candidate requires:

- reproducible baseline RED for every material behavior change;
- same-case GREEN and all applicable controls;
- no unauthorized consequential tool attempt;
- no false parent completion or forced continuation after explicit pivot;
- clear global/specialist ownership without duplicated mutable policy;
- valid panel lineage and cost ledger;
- provider-specific results with all veto findings adjudicated;
- truthful lifecycle metadata and compatibility decision;
- version/manifest/plugin/changelog/document synchronization;
- full structural validation, lifecycle audit, documentation audit, generated
  artifact stability, and install smoke;
- CI green on the exact release candidate;
- verified tag/release lineage and rollback evidence.

If any gate fails, the result is a documented candidate or a narrower compatible
release proposal, not a forced 6.0 release.

## Out of Scope

- Running Ollama or other local models.
- Claiming full Behavior coverage for all Skills without executable rubrics.
- Creating a standalone task-continuity Skill without independent routing proof.
- Rewriting unrelated domain Skills.
- Treating semantic judge agreement as executable GREEN evidence.
- Publishing a 5.9.0 placeholder solely to make version sequencing look linear.
