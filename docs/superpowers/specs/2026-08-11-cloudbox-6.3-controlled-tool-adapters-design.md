# CloudBox 6.3 Controlled Tool Adapters Design

**Status:** Approved design  
**Target:** CloudBox 6.3.0  
**Date:** 2026-08-11

## Purpose

CloudBox Skills currently guide engineering decisions and use repository-owned
scripts for validation, Eval exchange, provider adapters, Git synchronization,
and release support. CloudBox 6.3 will turn that partial pattern into a reusable,
controlled execution layer: Skills decide why and when a capability is needed,
while a versioned adapter performs one narrow operation and returns bounded,
verifiable evidence.

The goal is not to expose an unrestricted shell. The goal is a minimum vertical
slice that proves an adaptive lifecycle owner can plan, authorize, execute,
interrupt, reconcile, resume, and verify external CLI work without putting
arbitrary commands, credentials, or large logs into model context.

## Scope Decision

CloudBox 6.3 will implement a transport-neutral adapter contract, a controlled
local CLI broker, and a Git-based vertical slice. The contract may later support
MCP, but 6.3 will not implement an MCP server or live GitHub mutations.

The first Git capabilities are:

- `git.inspect`: obtain bounded repository and source identity evidence without
  changing repository state.
- `git.fetch`: update local refs only for a registered remote.
- `git.import_bundle`: import a versioned CloudBox exchange bundle through the
  existing integrity and compatibility boundaries.

Integration tests use temporary repositories and reversible fixtures. They do
not modify a real GitHub repository or an operator's configured remote.

## Alternatives Considered

### Transport-neutral contract with local CLI broker — selected

This option establishes the durable security, lifecycle, and evidence boundary
while reusing CloudBox's existing command-line and Git foundations. It provides
a real end-to-end path without requiring a service process, network protocol,
or host-specific MCP deployment in the same increment.

### MCP-first tool server

An MCP-first implementation would offer a standardized host integration sooner,
but it would combine contract design with service lifecycle, transport security,
deployment, and compatibility work. Those pressures are not necessary to prove
the execution semantics and would enlarge the first failure surface.

### CLI and MCP hybrid from the first release

A dual transport broker offers the most immediate flexibility, but requires
cross-transport conformance evidence before the authoritative contract has been
validated. CloudBox will keep the contract transport-neutral and defer the
second transport until the CLI vertical slice establishes usable evidence.

## Ownership and Architecture

The execution path has four layers:

1. `development-process-tailoring` is the lifecycle and plan owner. It selects
   the delivery flow, maintains stages and gates, reacts to risk and evidence,
   and decides whether work continues, returns to design, degrades, or stops.
2. The broker enforces capability registration, schemas, authority, action
   identity, idempotency, timeout, output, and secret boundaries. It never
   accepts a model-authored raw shell command.
3. A dedicated adapter implements only its registered capabilities. CLI and a
   future MCP transport must obey the same logical invocation and result
   contracts.
4. The external system remains authoritative for external side effects. A
   process exit or transport acknowledgement is evidence, not automatic proof
   that an external mutation completed.

Technical Skills define the evidence and constraints their operations require.
The host or coordinator grants authority. Adapters cannot expand that authority,
change the governing plan, or invent successful completion.

## Authoritative Contracts

One versioned registry is the source of truth for adapter identity and exposed
capabilities. Each entry defines:

- adapter and protocol versions;
- executable provenance and transport;
- capability name and input/output schema;
- `read-only`, `local-mutating`, or `remote-mutating` risk class;
- required authority and approval class;
- permitted secret references;
- timeout and retry eligibility;
- idempotency, cancellation, reconciliation, compensation, and recovery
  characteristics;
- bounded output and sensitive-field policy.

Invocation and result schemas are separate from the registry. An invocation
contains the registered adapter and capability, validated arguments, plan and
action identity, idempotency key, authority evidence reference, deadline, and
correlation metadata. A result contains the lifecycle state, structured output,
external resource identity, observed side effects, hashes, latency, cost where
applicable, and redacted diagnostics.

The registry follows the repository's existing authoritative-contract pattern.
Its validator must include positive propagation checks and negative drift
mutation tests rather than relying only on schema validity.

## Execution Safety

The broker launches only registered executables with validated argument arrays.
It does not evaluate a shell string, allow model-selected executables, accept an
unrestricted working directory, or inherit arbitrary environment variables.
Path arguments are resolved and checked against declared roots before launch.

Secret and private endpoint values never appear in the registry, repository,
Eval fixtures, logs, or model-visible result. The manifest declares secret
reference names; the host resolves an approved reference at execution time and
supplies only the minimum value required by the adapter. Results retain the
reference identity and redacted diagnostic evidence, not the value.

Third-party executables require an allowed source plus a pinned version or
digest policy. Unexpected executable or adapter drift fails closed. Mutating
capabilities additionally require an authority grant, stable action ID,
idempotency semantics, and a reconciliation method.

Raw logs and large artifacts remain outside model context. The broker returns a
bounded summary, hashes, artifact references, and only the diagnostic fields
needed for the next decision. Deterministic no-change checks must be able to end
without a model call.

## Durable Action Lifecycle

Each execution uses a durable `action_id` and transitions through:

```text
PLANNED -> AUTHORIZED -> RUNNING
                         |-> SUCCEEDED
                         |-> FAILED
                         |-> UNCERTAIN
                         |-> BLOCKED
```

- `SUCCEEDED` requires contract-valid evidence of the declared completion
  condition.
- `FAILED` means evidence proves the operation did not complete. Retry is
  allowed only when the capability policy and remaining attempt budget permit.
- `UNCERTAIN` covers timeout, disconnect, process loss, or ambiguous external
  completion. It must reconcile with the authoritative external system before
  retry or replacement.
- `BLOCKED` covers missing authority, secret, compatible adapter, dependency, or
  other unmet prerequisite. It preserves continuation evidence without claiming
  failure.

The durable checkpoint records the plan version, adapter and protocol versions,
validated input digest, authority evidence reference, action and idempotency
identity, lease/fencing evidence, external resource identity, result digest,
attempt budget, and allowed next transitions. Duplicate idempotency keys cannot
create a second side effect.

After interruption, the lifecycle owner loads this checkpoint, reconciles any
`RUNNING` or `UNCERTAIN` action, and then chooses resume, retry, re-plan,
degrade, return to architecture/design, or stop. An adapter may report changed
risk or environment evidence but cannot alter the plan itself.

## Tailored Delivery Lifecycle

The plan owner governs 6.3 as a two-iteration vertical-slice lifecycle:

1. **Baseline and contract iteration:** preserve current failure evidence,
   establish the authoritative schemas and registry, and prove one bounded path.
2. **Recovery and integration iteration:** exercise interruption, ambiguity,
   reconciliation, risk change, and adjacent Skill composition; then refine only
   the contract component responsible for observed failures.

Low-risk work with complete evidence may use a shortened path. Increased
authority, uncertain external state, executable drift, or broader side effects
adds a review or reconciliation gate. A discovered ownership or recovery error
returns the increment to architecture/design instead of being forced through a
release checklist.

The plan is durable and versioned. Risk events may change future work and gates,
but never rewrite completed evidence. A resumed session must be able to identify
the authoritative plan, completed stage, open action state, remaining budget,
and exact next safe command without relying on chat history.

## RED and GREEN Evidence

RED evidence must demonstrate that the current baseline does not provide the
new generic behavior. Repeatable cases cover:

- arbitrary shell or an unregistered adapter;
- a mutation without sufficient authority;
- timeout incorrectly treated as a safe immediate retry;
- a literal secret or private endpoint reaching logs or model output;
- adapter/version drift;
- duplicate action or idempotency identity;
- path escape and oversized output;
- interruption without a recoverable plan/action checkpoint;
- registry-to-consumer drift.

GREEN evidence must prove:

- the `git.inspect`, bounded `git.fetch`, and versioned bundle-import paths;
- fail-closed handling of every negative case above;
- reconciliation before retry from `UNCERTAIN`;
- durable plan-owner recovery and re-planning after interruption, changed risk,
  missing authority, and adapter failure;
- positive registry propagation and negative drift mutations;
- adjacent routing and behavior regressions, including the distinction between
  lifecycle ownership, agent tool design, repository governance, and Skill
  development;
- package, documentation, installation smoke, and complete deterministic checks.

A passing schema or structural validator is not a behavioral pass. Any material
Skill change must begin with RED behavior evidence and re-run the same case for
GREEN.

## Documentation and Operations

Operator documentation will explain how to:

- register a narrow adapter without exposing arbitrary command execution;
- configure secret references outside the repository;
- inspect, dry-run where applicable, execute, interrupt, reconcile, and resume;
- locate bounded summaries and full local artifacts;
- migrate or disable an incompatible adapter;
- retain the existing manual Git/bundle path when automation is unavailable.

The increment updates the README, design and flow, change history, operational
handoff, release evidence, and authoritative version surfaces. Documentation
must distinguish implemented CLI behavior from deferred MCP and live external
integration.

## Explicit Non-goals

CloudBox 6.3 does not include:

- unrestricted shell execution;
- live GitHub pull request, merge, tag, or Release automation;
- NAS polling or a persistent monitoring daemon;
- an MCP server implementation;
- public/private package splitting;
- repository storage of private URLs, credentials, personal data, or sensitive
  extracted material;
- automatic approval or authority expansion by a Skill, broker, or adapter.

## Release Gate

6.3.0 may be prepared only after the same RED cases are GREEN, adjacent
regressions and deterministic checks pass, the lifecycle owner demonstrates
interruption and reconciliation from durable evidence, and the release record
truthfully distinguishes fixture execution from live external operations.
Publication, GitHub mutations, hosted model review, tag creation, and Release
remain separate actions governed by their existing authorization and evidence
rules.
