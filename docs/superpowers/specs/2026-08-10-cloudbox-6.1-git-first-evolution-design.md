# CloudBox 6.1 Git-first evolution design

**Status:** approved for implementation planning  
**Target:** CloudBox 6.1.0  
**Related:** GitHub issue `#6`

## Outcome

CloudBox 6.1 adds a versioned manual candidate exchange and a portable,
token-free Git change-ingestion path. It also adds a shared architecture
decision-elicitation protocol. Background work may discover, sanitize,
deduplicate, and store candidates, but it may not invoke a model, modify a
Skill, commit, push, open a PR, or publish a release.

NAS directory watching is deferred to 6.2. The 6.1 CLI must remain portable so
the later NAS runner can call the same contracts without reimplementing them.

## Workstream A: architecture decision elicitation

Create one shared reference for architecture-oriented Skills, including
`architecture-review`, `application-client-server-architecture`,
`cross-platform-engine-architecture`, `cross-platform-native-architecture`,
`equipment-control-architecture`, and `framework-design` where their existing
trigger applies. Do not route every architecture task through
`architecture-review`.

The protocol asks one question at a time only when the missing answer can
materially change authority, state, lifecycle, transaction, deployment,
recovery, security, migration, or release conclusions. Each question offers
two or three mutually exclusive choices, places the recommended option first,
and explains its mechanism and trade-off. It must not ask when repository
evidence already answers the question, when the task is explanatory or purely
diagnostic, or when a safe low-risk reversible default is sufficient.

Before changing Skill instructions, preserve RED behavior cases for:

- a review that prematurely recommends an architecture without resolving a
  material authority decision;
- a green-field engine design that needs clarification without being routed
  through `architecture-review`;
- a complete-evidence review that must proceed without needless questions;
- an explanation, isolated code review, or trivial reversible task that must
  not trigger the protocol.

The same cases must turn GREEN after the smallest owner/reference change, with
adjacent routing regressions and behavior execution reported separately from
structural validation.

## Workstream B: versioned manual export and import

Manual capture, export, ZIP transfer, import, Inbox review, and Exchange
push/pull remain supported, but the exporter and importer advance together to
a new explicit format. No old-bundle migration is required because the feature
is new and accumulated bundles are limited.

Every export contains a manifest with at least:

- `bundle_format_version`;
- `cloudbox_version`;
- `exporter_version`;
- `candidate_schema_version`;
- `host` (`codex`, `claude`, or another registered host);
- `agent_name`;
- `export_project_name`;
- UTC creation time;
- collision-resistant `bundle_id`;
- relevant schema and payload hashes.

The first interactive export for a project asks for an export project name and
stores it in the ignored project-local `.cloudskill/config.local.json`.
Subsequent exports reuse it without asking. Users may change it explicitly.
Names are normalized to safe filename characters and cannot contain path
separators or control characters. A non-interactive export without a configured
name fails safely with an actionable message; it never guesses from a private
path.

Bundle filenames use:

```text
<project>-<host>-<agent>-<UTC YYYYMMDDTHHMMSSZ>-<short bundle ID>.zip
```

The short ID is mandatory because two machines may export within the same
second.

The 6.1 importer accepts only its declared supported format range. A legacy or
unknown bundle is not partially imported, migrated, rewritten, or deleted. It
is classified `UNSUPPORTED`, retained for inspection, and accompanied by an
explicit inspection and deletion command. Deletion is a separate user action
and is prohibited in CI/background synchronization. Already imported Inbox
candidates remain available and may receive a new index; the incompatibility
rule applies to unimported legacy bundles.

## Workstream C: Git-first source synchronization

### Components

1. **Source Registry** validates logical `source_id`, source type, secret
   references, ref/path scope, and mining bounds. Public examples contain only
   placeholders.
2. **Secret Resolver** obtains actual source/destination URLs and credentials
   from environment/CI/NAS secret injection or ignored local configuration.
   URLs are sensitive. Neither URL nor credentials may enter logs, errors,
   prompts, bundles, candidates, or public evidence.
3. **Git Change Detector** compares remote refs and content fingerprints with
   durable last-seen state. No change ends the run before checkout or model use.
4. **Mining Pipeline** performs a bounded temporary checkout, selects allowed
   history/doc/code evidence, sanitizes, normalizes, scans, and deduplicates.
   Project-history confidence remains `inferred` or `unknown`, never
   `observed`.
5. **Private Exchange Store** uses one user-owned private repository partitioned
   by `source_id` into candidates, manual review, rejected, quarantined,
   provenance, and state.
6. **Review/Evolution Controller** exposes manual commands for review,
   evaluation, Skill application, and release. GitHub Actions
   `workflow_dispatch` is only an adapter over these commands.

### State and storage

The private Exchange retains all sanitized accepted, manual-review, rejected,
and quarantined candidate records. It does not retain a full source repository
copy. Content that cannot be established as safely sanitized stays quarantined
and cannot reach a model or formal Eval.

Private provenance records the true logical source mapping, commit/ref, content
hash, processing decisions, and transition history. Public CloudSkill changes
carry only a non-reversible anonymous evidence ID, generalized engineering
pressure, and sanitized tests. A private mapping may prove the relationship;
the public ID must not reveal a URL, repository name, path, account, or commit.

The state machine is:

```text
DISCOVERED -> FETCHED -> SANITIZED -> STORED -> REVIEW_PENDING
           -> ACCEPTED | REJECTED | QUARANTINED
```

Checkpoints advance only after candidate and provenance persistence succeeds.
The same ref/content rerun is idempotent. Interrupted fetch, store, Exchange
push, or checkpoint operations reconcile before retry. An Exchange write
failure cannot mark work complete. Late completions are correlated by operation
ID and reconciled rather than blindly repeated.

### Authority and credentials

- Source credentials are read-only and separate from the Exchange write
  credential.
- The background authority envelope ends at sanitized private candidate
  persistence and checkpoint update.
- Model calls, formal Eval conversion, Skill edits, Git commits, pushes, PRs,
  tags, and releases require explicit manual commands.
- Logs expose only logical IDs and non-reversible short fingerprints.
- Candidate/export bundles contain no connectivity settings.
- Credential rotation changes secret values without changing Skill or public
  configuration.

### Entry points

The CLI is authoritative and portable across local machines, GitHub Actions,
self-hosted CI, and a later NAS runner. User-facing operations include these
stable concepts, while exact executable names are fixed in the implementation
plan:

```text
sync source
review candidate
evaluate candidate
apply evolution
release evolution
inspect unsupported bundle
delete unsupported bundle
```

GitHub Actions provides a scheduled/ref-triggered synchronization example and
manual `workflow_dispatch` wrappers. It may not duplicate state transition or
authorization logic.

## User-facing phrases and documentation

- `從專案提煉優化案例`: first bounded project-history mining pass.
- `同步優化來源`: recurring/incremental Git source synchronization.
- `匯入優化候選`: import a supported manual bundle.
- `審核優化候選`: sanitize/deduplicate/ownership review.
- `評估演化候選`: explicitly authorized evaluation.
- `執行技能演化`: apply an approved evidence-gated change.
- `發布技能演化`: run release gates and publication.

Do not use `採集技能` as the primary phrase because it can be confused with
installing Skills.

Add a detailed operator guide and a concise README entry linking to it. The
guide documents manual and automated paths, supported bundle versions, upgrade
verification across machines, private URL/credential configuration by secret
reference, inspection/deletion of unsupported bundles, public-control/private-
storage boundaries, recovery, and rollback.

## Verification and release gates

Executable RED/GREEN and mutation coverage must prove:

- architecture tasks ask only when a material decision is unresolved;
- no-change synchronization performs zero model calls;
- the same source ref/content cannot create duplicate candidates;
- public and private source scope is enforced;
- URLs, credentials, and private paths remain redacted on success and failure;
- candidate/provenance/checkpoint partial failures recover without false
  completion;
- uncertain sanitization can only become quarantined;
- background execution cannot reach evaluate/apply/release actions;
- CLI and GitHub Actions adapters produce the same result for the same fixture;
- filename normalization, same-second collision resistance, version metadata,
  interactive name persistence, and non-interactive missing-name refusal work;
- unsupported bundles remain unimported and undeleted until a separate explicit
  deletion action;
- existing manual capture/import concepts and already-imported Inbox candidates
  remain usable.

Before 6.1.0 publication, run structural, description, routing, behavior,
composition, install-smoke, deterministic, recovery, redaction, and release
checks. Record model behavior execution truthfully. Use the established 6.0
evidence-gated multi-model release process for release-significant Skill
behavior changes.

## Deferred to 6.2

- NAS folder watching and ten-minute filesystem scans;
- automatic model invocation on detected changes;
- automatic Skill modification, commit, push, PR, merge, tag, or release;
- legacy bundle migration;
- public storage of actual URLs, credentials, private paths, raw sources,
  candidates, or transfer state.
