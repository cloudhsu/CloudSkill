# Document Type Selection

## Requirement Specification

Use when defining mandatory outcomes and constraints.

Must emphasize:

- Stable requirement IDs.
- Source/rationale.
- Acceptance criteria.
- Priority.
- Dependencies.
- Traceability.

## Architecture Decision Record

Use for a bounded architectural choice.

Must include:

- Context.
- Decision.
- Considered alternatives.
- Consequences.
- Status.
- Revisit conditions.

## Architecture or Design Specification

Use when implementation boundaries and runtime behavior must be understood.

Must include:

- Responsibilities.
- State ownership.
- Interfaces.
- Data/command flow.
- Failure/recovery.
- Concurrency.
- Deployment.
- Verification.

## Test Plan or Verification Specification

Use when evidence must be repeatable.

Must include:

- Requirement links.
- Test environment.
- Preconditions.
- Steps or method.
- Expected result.
- Evidence.
- Pass/fail rule.
- Exceptions.

## Release Notes

Use for users, operators, service staff, and maintainers.

Separate:

- Added.
- Changed.
- Fixed.
- Known limitations.
- Upgrade/migration.
- Rollback.
- Compatibility.
- Field impact.

## Incident or Field Issue Report

Separate:

- Observed symptom.
- Operational impact.
- Timeline.
- Affected versions.
- Evidence.
- Containment.
- Root cause.
- Corrective action.
- Preventive action.
- Verification.
- Release linkage.

## Multi-Audience Quality Report

Recommended views:

- Raw data and exclusions.
- Management impact and trends.
- Engineering root cause and corrective learning.

Do not let summaries alter the underlying counting rules.
